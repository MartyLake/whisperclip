# Phase 11.4: Nemotron 3 Diarizer - Context

**Gathered:** 2026-10-13
**Status:** In progress — implementation and automated validation are complete; manual audio UAT is pending.

<domain>
## Phase Boundary

System-audio speaker attribution moves from FluidAudio's `DiarizerManager` (pyannote segmentation +
WeSpeaker embeddings + online clustering) to NVIDIA Nemotron 3 Diarization, run on-device through
FluidAudio's `Nemotron3Diarizer` (CoreML). The old path is deleted, not kept as a fallback.

In scope: the streaming diarizer, a speaker timeline the rest of the app can query, model
download/management, wiring into the existing closed-buffer pipeline, removal of the old path.

Out of scope: retroactive relabelling and splitting of already-shown segments (Phase 13), chat bubbles
(Phase 12), named speakers across meetings (Phase 14), the STT-readiness check and orphaned-folder
cleanup from finding D-1 (unscheduled, see `IDEAS.md`).

</domain>

<decisions>
## Implementation Decisions

- **D-01: No Hugging Face token in this phase (reverses the 2026-10-13 plan).** The roadmap assumed
  `FluidInference/nemotron-3-diarization-coreml` was gated. Checked on 2026-10-13: the Hub API reports
  `gated: false`, `private: false`, and a file downloads anonymously (HTTP 200). TOKEN-01..03 are
  therefore not needed to ship this phase and are moved to `IDEAS.md`. If the repo becomes gated again,
  FluidAudio reads the token from the `HF_TOKEN` / `HUGGING_FACE_HUB_TOKEN` environment variables only.
- **D-02: `DiarizerManager` is removed.** Per the owner it never produced usable attribution. Its
  wiring, the chunk-based `DiarizationProvider` protocol, the micro-window/dominant-speaker logic in
  `SpeakerBufferManager`, the old model download in Onboarding and their tests all go.
- **D-03: Default preset `fast32`** (2.56 s of audio per call, 2.88 s latency, 9.53 DER on AMI — the
  model card's recommended default). `fast` (1.04 s) and `fast128` (10.56 s) are selectable. Each preset
  is a separate ~199 MB download; only the selected one is fetched.
- **D-04: Speaker labels come straight from slot order.** Nemotron 3 orders its 8 output slots by first
  arrival and keeps them for the stream, so slot `i` is "Speaker `i+1`". No label map, no clustering.
- **D-05: The timeline is the product of this phase; closed buffers are derived from it.** A
  `SpeakerTimeline` value type holds per-frame activity and answers "who spoke between t0 and t1".
  `SpeakerBufferManager` cuts audio at timeline turn boundaries and emits the same `ClosedSpeakerBuffer`
  stream as today, so `MeetingRecorder.transcribeClosedBuffer` is unchanged. Phase 13 reads the same
  timeline.
- **D-06: System-audio rows appear later than today.** Labels exist only once the diarizer has seen
  `latencySeconds` of audio past a frame, so a system-audio pending row appears ~3 s after speech starts
  on `fast32` (today: about 1 s, with an unreliable label). Accepted for this phase; Phase 13 restores
  immediate pending rows by creating them unlabelled and resolving them from the timeline.
- **D-07: No model, no diarizer.** If the selected preset is not downloaded or fails to load, the app
  uses the existing source-based path (mic → "Me", system audio → one unattributed remote speaker) and
  the UI says speaker separation is off and offers the download. Recording is never blocked by it.
- **D-08: Overlapping speech goes to the most active slot.** A closed buffer has one label. Per frame
  the slot with the highest probability above threshold wins; simultaneous speakers are not duplicated.
- **D-09: The microphone channel stays "Me"** with no diarizer (decision of 2026-03-23).

</decisions>
